# 通过 Push-T 学会构建自定义任务：源码讲解与小实验结合的学习路线

导出日期：2026-10-02。以下为原对话中的完整学习计划，仅整理 Markdown 标题层级。


你已经了解模块名称和基本职责。接下来建议围绕一个问题展开：**给定任务需求，为什么需要这些模块，它们之间必须约定什么，怎样验证它们能协同工作？**

采用你希望的两种方式结合：每个阶段先系统讲解设计和源码，再用一个小实验验证理解。先以 **低维 Push-T + U-Net Diffusion Policy** 贯通完整流程，然后学习图像版的变化，最后完成一次任务接口改造。

## 学习顺序

1. **先把 Push-T 写成一份任务需求，再理解 Env 如何实现它。**

   从 [pusht_env.py](/home/jiyuchen/project/WYS/diffusion_policy/diffusion_policy/env/pusht/pusht_env.py:28) 开始，依次回答：控制谁、能看到什么、动作表示什么、什么时候成功、一轮任务什么时候结束。

   重点区分环境内部状态、策略观测和控制动作。例如，环境内部包含推块器位置、T 块位置和角度；默认低维策略接收的是关键点与推块器位置；二维动作表示推块器的目标位置。还要理解控制频率、物理仿真频率、覆盖率奖励之间的关系。

   小实验：固定初始状态，输入几个位置指令，观察状态和奖励变化。阶段产出是一张“任务需求 → 环境接口 → 对应代码”的表。学完应能解释，自定义任务需要在 Env 中确定哪些行为。

2. **跟踪一条示范，从采集到训练样本。**

   沿着示范采集脚本、ReplayBuffer、[PushTLowdimDataset](/home/jiyuchen/project/WYS/diffusion_policy/diffusion_policy/dataset/pusht_dataset.py:12) 和 SequenceSampler，追踪同一条轨迹。

   重点解释：如何对应 `obs_t` 与 `action_t`；为什么记录 episode 边界；如何切长度为 `T` 的窗口；开头和结尾怎样补齐；训练与验证如何按 episode 组织；原始字段如何变成策略输入。

   小实验：取出一条 episode，再查看开头、中间、结尾的三个训练窗口，逐项核对索引、形状和数值。随后检查归一化及反归一化能否恢复原始动作。

   阶段产出是完整的数据变换表：**原始字段 → 采样窗口 → Dataset 样本 → DataLoader 批次 → 归一化后的输入**。

3. **用一个 batch 理解 Policy 的训练和推理。**

   阅读 `DiffusionUnetLowdimPolicy` 的 `compute_loss()`、`conditional_sample()` 和 `predict_action()`，跟踪这个 batch 在各步骤中的变化。

   训练侧关注观测条件、动作加噪、噪声预测和损失；推理侧关注随机初始化、迭代去噪、反归一化和动作截取。第一轮只需理解 U-Net 的输入、输出和条件如何接入，网络内部结构留作后续专题。

   用默认的 `To=2、T=16、Ta=8` 画出时间轴，解释为什么完整预测与实际执行长度不同，以及扩散去噪次数为什么属于另一个时间维度。

   小实验：计算一次损失并反向传播，再调用一次动作预测，核对完整轨迹与执行片段。学完应能说清楚新任务需要怎样适配输入输出，以及哪些情况下能够复用现有 Policy。

4. **从配置出发，理解 Workspace 怎样组装训练流程。**

   从 [pusht_lowdim.yaml](/home/jiyuchen/project/WYS/diffusion_policy/diffusion_policy/config/task/pusht_lowdim.yaml:1) 和对应方法配置出发，追踪 Hydra 怎样把配置中的 `_target_`、插值和覆盖参数变成对象。

   然后沿 `train.py → Workspace.run()` 阅读，找到 Dataset、DataLoader、Policy、优化器、EMA、归一化器和 Runner 的创建位置。区分训练损失、验证损失和环境评估分数，并说明 checkpoint 保存什么、如何恢复。

   小实验：先核对依赖和数据能否使用，再进行一次受限的短训练，保存并重新加载 checkpoint。使用独立输出目录和关闭在线日志的配置。

   阶段产出是一张对象创建及调用图，能够指出“更换数据、任务、模型、训练参数”分别应该改哪里。

5. **跟踪一次闭环评估，理解各模块如何共同完成任务。**

   沿 `EnvRunner.run(policy)` 跟踪：环境初始化、历史观测堆叠、张量转换、策略预测、动作执行、新观测返回和指标汇总。

   在这里重点讲清 `MultiStepWrapper`：底层环境逐步执行动作，上层策略一次接收多步观测并返回一段动作。随后再看多环境并行和视频记录，理解它们如何包裹这个基本循环。

   小实验：在固定种子的少量环境中完成短 rollout，记录每次预测前后的观测和动作形状。区分“程序闭环能运行”与“策略已经学会完成任务”，并核对 Push-T 的 `mean_score` 具体如何计算。

   阶段产出是一张推理时序图，能解释离线训练和在线环境评估怎样连接。

6. **把图像版作为一次接口扩展案例来学习。**

   对照低维版，逐项分析图像观测环境、图像 Dataset、`shape_meta`、视觉编码器和图像 Runner 的变化。重点理解图像与机器人状态怎样同时进入策略，以及训练数据和运行时观测如何保持一致。

   小实验：查看同一条示范在两种 Dataset 中的表示，核对图像通道顺序、数值范围、时间维度和动作语义。

   阶段产出是一张迁移表：**改变观测后，哪些模块需要修改，哪些接口保持一致，哪些实现可以复用。**

7. **用一次小改造检验是否具备自定义任务接入能力。**

   利用现有 Push-T 数据，把低维观测改为六维：推块器位置、T 块位置，以及角度的正弦和余弦。这个练习保留现有任务行为，集中练习任务接口的设计和接入。

   先写观测定义，再同步设计 Dataset、环境观测、Runner 与任务配置，复用现有低维 Policy 和 Workspace。尤其核对数据中的角度与环境实时角度是否采用一致的表示。

   验收包括：离线与在线观测语义一致、归一化可逆、训练与推理形状正确、checkpoint 可恢复、短闭环评估能运行。最终整理成一份可用于新任务的接入清单。

## 每一阶段的讲解方式

固定采用“需求是什么 → 设计为什么如此 → 关键代码怎样实现 → 数据如何流动 → 小实验验证 → 自定义任务需要迁移什么”的顺序。这样每次读代码都有明确的问题，也有可检查的学习结果。

当前默认以仿真任务接入为主线；真机时间同步、机器人控制器和多相机进程，等你明确具体任务后再扩展。完整训练获得高分属于后续性能验证，前面的实验先验证模块与接口是否正确。

**第一步就从任务定义开始。** 第一轮只需要围绕 Push-T 写清楚六项：目标、观测、动作、时间频率、初始化方式、成功与终止条件；然后逐项映射到 Env。接下来再沿同一份定义追踪示范数据，会更容易理解每个模块为什么这样构建。
